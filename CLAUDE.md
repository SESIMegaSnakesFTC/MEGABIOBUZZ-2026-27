# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An Android Studio / Gradle project built on the FIRST Tech Challenge (FTC) SDK for the **BIOBUZZ (DECODE 2026-2027)** season. It controls a real competition robot (team Mega Snakes) via the FTC Driver Station + Control/Expansion Hub. There is no backend/web layer — all code runs on the robot's Android control hub. See `README.md` for the game rules (HIVE/CELL/FLOWER scoring) in more depth; the short version: the robot shoots POLLEN/NECTAR into a HIVE pivot (tracked via AprilTags) and later scores at FLOWERs.

Two Gradle modules (see `settings.gradle`):
- **`FtcRobotController`** — the stock FTC SDK app module. Avoid modifying unless the task is explicitly about SDK-level behavior; prefer putting robot logic in `TeamCode`.
- **`TeamCode`** — the team's actual code, under `TeamCode/src/main/java/org/firstinspires/ftc/teamcode/`. This is where almost all work happens.

## Build / install commands

- `./gradlew build` — full build of both modules.
- `./gradlew :TeamCode:assembleDebug` — build just the TeamCode APK.
- `./gradlew :TeamCode:installDebug` — build and install onto a connected/ADB-attached Control Hub.
- There is **no unit/instrumented test suite**. "Testing" means deploying an OpMode and running it on the physical robot (or in the Driver Station app) — there is nothing to run headlessly. Classes under `Testes/` (and other `@Disabled`/experimental OpModes scattered through the tree) are manual hardware test rigs, not automated tests.
- Dependency/version config lives in `build.dependencies.gradle` (FTC SDK libs pinned to `12.0.0`, plus Pedro Pathing `com.pedropathing:core:3.0.0` / `revhub:3.0.0` / `telemetry:1.0.0` / `tuning:1.0.0`, Pedro Ivy `com.pedropathing.ivy:pedro:1.1.1`, and `com.bylazar:fullpanels:1.0.12`; the Pedro API changes a lot between major versions — e.g. `PoseFactory.mirrorX`/`mirrorY` require an explicit axis argument in `3.0.0`, there is no no-arg overload — so write code against these exact pinned versions, not against memory of older ones). `build.common.gradle` holds shared Android build config (compileSdk 34, minSdk 24, targetSdk 28, Java 8 source/target) — per its own header comment, avoid editing it; put customizations in `TeamCode/build.gradle` instead.

## Architecture

Code under `teamcode/` is organized by role, not by season feature, and most packages mix Portuguese and English names (team is Brazilian). New comments go in Portuguese (see team rules below); class/method names follow whatever the surrounding file already uses. No subsystem is a DI/"robot container" — every `Mech/*` class is a plain object (`new Chassi()`, etc.) instantiated directly inside each OpMode, following `init(hardwareMap)` + per-loop methods (`drive(x,y,rx)`, `Activate(bool)`, `update(...)`).

- **`Mech/`** — thin hardware-subsystem wrappers. `Chassi` (mecanum drive, power-normalized), `Shooter` (velocity-PIDF flywheel on motor `"shooter"`; battery-voltage feedforward compensation; takes an optional `VoltageSensor` in its constructor, falling back to looking one up itself in `init` if none is passed), `Feeder`/`MidTake` (feeding motors), `ValuesToShoot` (a `TreeMap<distance, {hoodPos, motorPower}>` lookup table with floor/ceiling interpolation — the single place that maps Limelight distance to shooter/hood targets; `Double.NaN` entries mean "not measured yet", callers must hold the last good value), `LimeLight` (wraps `Limelight3A`, pipeline switching per alliance/side), `IMU_Initializer`, `PinpointConf` (GoBilda Pinpoint localizer factory used by TeleOp — note it has its own pod offsets, separate from `Autonomo/pedro/Constants.java`'s `PinpointConfig` used by autonomous; keep both in sync when retuning odometry), `TurnOn_TurnOff` (generic rising-edge toggle-latch helper used everywhere a gamepad button should flip a boolean state).
  - **`Mech/Servos/`** — `FlowerServo`, `GateServo` (feeder gate, opens once the shooter has had time to spin up), `HoodServo` (adjusts shooter hood angle, driven by `ValuesToShoot`), `RampServo`.
    - **`Mech/Servos/ToTurret/`** — `TestingAtritServo`, `TrackingTurretServo`, `TurretServo` — earlier servo-driven turret experiments, superseded by the motor-driven turret below.
  - **`Mech/c270/`** — `Functions`, an AprilTag-via-webcam experiment using the stock FTC `VisionPortal`/`AprilTagProcessor` rather than Limelight.
- **`Mech/Turret/`** — the turret aiming subsystem, the most involved piece of logic in the repo:
  - `TurretConfig` — all tunable constants (PID-ish gains `kP/kD/kS/kV`, angle limits, deadband, vision/tracking timing like `maxStaleMs`/`lostTimeoutMs`/`confirmFrames`, plus a `PoseCorrection` sub-block for `VisionPoseCorrector`'s gains/filters). Treat as the single place to retune turret behavior.
  - `TurretController` — owns the turret `DcMotorEx`; converts an angle target into motor power using proportional + static-friction + velocity-damping + chassis-rotation-feedforward terms, with battery-voltage compensation and soft limits at `minDeg`/`maxDeg`. Degrees are tracked unwrapped (can exceed ±360) so `setTarget` picks the nearest equivalent angle within range.
  - `TurretTracking` — a 2-state (`ODO` / `TRACK`) estimator that fuses chassis odometry heading with Limelight AprilTag detections: while a target hive's tag is visible it low-pass-filters a bias between vision-measured angle and odometry-predicted angle; when vision is lost/stale it falls back to pure odometry. Also estimates chassis angular velocity from heading deltas for the controller's feedforward term. `onPoseCorrected()` must be called whenever `VisionPoseCorrector` applies a correction, so the bias isn't double-counted.
  - `HiveTracking` — pure geometry/game-state helper: given alliance + starting pose, tracks which of the two "hives"/cells (upper/lower) the robot should currently aim at (with Y-axis hysteresis to avoid flip-flopping near the midline), and computes the odometry-only turret angle and distance to the active hive. Also owns the AprilTag ID sets per hive/alliance — **blue cell tag IDs are still `TODO`**, and there is no field map yet for the blue AprilTags (only `Limelight/hives_vermelhas.fmap` for red 30-37); don't assume blue tracking works end-to-end.
  - `VisionPoseCorrector` — corrects the Pinpoint odometry pose using the Limelight's MegaTag1 `botpose`. Keeps a ~1s history of (time, odometry pose, turret angle) to compensate for Limelight latency, converts the camera pose to robot pose accounting for the turret (camera is mounted on the turret, so the Limelight's own "Camera Pose in Robot Space" must stay all-zero), rejects bad samples (stale/few-tags/far/moving/out-of-field/yaw-mismatch/outlier — see the `Status` enum), and applies the averaged correction with a gain every `correctionIntervalMs`. Used by every active TeleOp and `*Mech` autonomous.
  - `TurretTunning` (in `Mech/Turret/`, note the misspelling) — live-tuning TeleOp for the turret, analogous to `PIDS/TunningShooters` for the shooter.
- **`Autonomo/pedro/`** — integration with the third-party **Pedro Pathing** library (`com.pedropathing:*`) for localization/path following, autonomous.
  - `Constants.java` is the single source of truth for drivetrain (`MecanumConfig`), localizer (`PinpointConfig`), and motion-profile (`ForesightConfig`) tuning values, and exposes `Constants.create(hardwareMap)` to build a `Follower`. This is the canonical path to get a configured `Follower`, in preference to constructing one by hand.
  - `procedures/` (`PinpointTuner`, `MecanumTuner`, `ForesightTuner`, `OTOSTuner`, `ThreeWheelTuner`, `ThreeWheelIMUTuner`, `TwoWheelTuner`, `OctoQuadTuner`, etc.) are Pedro Pathing's own auto-tuning `Procedure`/`TuningOpMode` boilerplate, generated/structured by the library's tuning tool — treat as mostly vendor code; `Tuning.java` is the entry OpMode that runs them.
  - `Ivy/` holds the active autonomous style, built on **Pedro Ivy** (`com.pedropathing.ivy:pedro`), a command scheduler. **`Ivy/Ivy_model.java` (`@Disabled`) is the template to copy** when creating a new autonomous — unlike a bare path-follow skeleton, it already wires up the full mechanism loop (turret, shooter, feeder, gate, hood, `VisionPoseCorrector`) the same way the real routines below do, so copy it rather than building the mechanism plumbing from scratch. Pattern: a package-private `<Name>Path` class in the **same file** defines waypoint `Pose`s (via `PoseFactory.degrees()`) and builds `Path`s with `com.pedropathing.api.Paths.line/curve`; the public `@Autonomous` class (an iterative `OpMode`, not `LinearOpMode`) calls `Scheduler.reset()` + `Constants.create(...)` + `follower.setPose(...)` in `init()`, schedules a command tree (`sequential`/`parallel` of `follow(follower, path)`, `waitMs`, `instant(() -> ...)`, `waitUntil(...)`, `hold(follower)`) in `start()`, and runs `follower.update(); Scheduler.execute(); atualizarMecanismos();` in `loop()` — the mechanisms update every loop regardless of scheduler state, driven by boolean flags the schedule flips via `instant(...)`.
    - Real routines live one subfolder per starting position: `Ivy/RedDown/` (`RedDownMech`, `RedFlower`, `SoloRedDownMech` — all full mechanism routines; `SoloRedDown` is a lighter path-only, `@Disabled` variant of the Solo route), `Ivy/RedUp/` (`RedUpMech`), `Ivy/BlueUp/` (`BlueUpMech`, currently **work in progress / uncommitted** — its `PoseFactory.degrees().mirrorY()` call is missing the required axis argument and won't compile yet, and its `START` constant is set to `BLUE_DOWN` despite the file/Autonomous name saying "Up"). There is no `BlueDown` yet.
    - Naming convention: a `*Mech` suffix (e.g. `RedDownMech`) means the full subsystem loop (turret/shooter/feeder/gate) runs alongside path following; a bare name (e.g. `RedFlower`, `SoloRedDown`) is path-following only, usually `@Disabled`.
    - **Selecting a route:** there is no automatic selector — each starting position/strategy is a separate `@Autonomous` OpMode chosen by name on the Driver Station.
  - `WarmUp_WithoutPedro/` (at `Autonomo/WarmUp_WithoutPedro/`) — simpler autonomous variants that don't depend on Pedro Pathing (direct encoder/time-based moves: `AzulBaixoPARK`, `HiveDownOneTip`, `HiveUpOneTip`, `HiveUpTwoTips`, `Modelo`), used as warm-up/fallback routines. These still target the older **two-motor** shooter config (`"leftShooter"`/`"rightShooter"`), not the current single `"shooter"` motor.
- **`PIDS/`** — `RobotPID.java` is a standalone heading PID controller (not tied to Pedro Pathing or the turret), for use in simpler/manual control loops; `TunningShooters.java` is a TeleOp for live-tuning the shooter's velocity PIDF. Note: it declares a `midTake` field but never fetches it via `hardwareMap.get(...)` before calling `setDirection`/`setPower` on it — will NPE if actually run with that code path hit.
- **`TeleOperados/`** — the real competition TeleOps: `TeleOp_BLUE.java` / `TeleOp_RED.java`, each a `LinearOpMode` wiring together `Chassi` (gamepad1 sticks), the full turret/tracking/`VisionPoseCorrector` stack (gamepad1 `A`/`B`/`X` toggle tracking/vision/pose-correction the same way the autonomous `*Mech` routines do), and feeder/midtake/shooter/gate (gamepad2). `TeleOpWarmUp/TeleOpFlowerServo.java` (`@Disabled`) is an in-progress/scratch OpMode.
- **`Another_Codes/`** — `Moviment.java` (plain mecanum TeleOp over `Chassi`, using `LynxModule` bulk caching) and `MovimentAndFeeder.java` (adds feeder testing).
- **`Testes/`** — manual hardware test rigs, not automated tests. `TestTrackingOnChassi.java` is the best current reference for how the turret subsystem composes with odometry + Limelight outside of a full autonomous/TeleOp (gamepad A toggles odometry-only tracking, B toggles Limelight-assisted correction, X toggles pose correction); `podsTest.java` and `testMotor.java` are simpler one-off rigs.

## Conventions worth knowing

- Hardware device names passed to `hardwareMap.get(Class, "name")` (e.g. `"leftFront"`, `"turretMotor"`, `"pinpoint"`, `"limelight"`, `"shooter"`) must match the robot's physical hardware configuration on the Driver Station/Control Hub exactly — renaming one in code without updating the on-robot config (or vice versa) breaks the OpMode at runtime, not at compile time.
- Angles throughout the turret/tracking code are in **degrees**, field heading is **unwrapped** (continuously accumulated, not wrapped to ±180) where used for feedforward, and `normalize180`-style helpers are used when wrapping is actually needed — keep this distinction when touching that code.
- Pedro Pathing's `PoseFactory.mirrorX(axis)`/`mirrorY(axis)` (used to derive one starting position's poses from another) both require an explicit `axis` argument in the pinned `core:3.0.0` — `mirrorX` also negates heading, `mirrorY` keeps heading unchanged. There's no parameterless overload; a bare `.mirrorY()` is a compile error.
- Subsystem classes follow `init(hardwareMap)` + stateless-ish per-loop update methods; they're plain objects instantiated directly in OpModes, not a DI/subsystem-manager framework — there's no shared robot "container" class to register into.

## Regras da equipe

- Sempre responder em português, de forma direta e clara.
- Comentários no código em português, curtos e claros.
- Antes de realizar uma alteração no código, dê ao menos uma boa ideia de implementação (caso haja).

  1. `Add:` arquivos/classes novos adicionados
  2. `Fix:` problemas corrigidos e em quais arquivos
  3. `Implement:` lógica nova implementada e em quais classes
  4. `Refactor:` arquivos movidos/renomeados, reorganização sem mudar lógica
- Antes de commitar, propor a mensagem nesse formato e aguardar aprovação; só depois fazer o push.
- Sempre perguntar antes de executar um código e explicar brevemente usando a skill caveman
